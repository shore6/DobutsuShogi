# 開発ロードマップ

仕様書：[SPEC.md](SPEC.md)

## 進め方

各マイルストーンは「動く状態」で区切る。
一つ終えるごとに CLI から結果を確認でき、テストが通る状態を保つ。

## M0：土台　（完了）

**目標**：空のライブラリがビルドでき、テストが 1 件通る。

- CMake プロジェクトの構成（ライブラリ、CLI、テストの 3 ターゲット）
- GoogleTest の取り込み
- `types.hpp`：`Color`, `PieceType`, `Piece`, `Square` の定義と基本操作
- 座標変換（マス連番 ↔ 筋段、文字列 `2c` との相互変換）

**完了条件**：`ctest` が緑になる。

**設計判断**：駒を 1 バイトに詰める際のビット配置。
手番を上位ビットに置くか下位に置くかで、`piece_type()` と `color_of()` のコストが入れ替わる。
どちらを高頻度と見るかを決める。

→ 上位ビットに手番を置くことに決定した。
これを含む M0 の決定 6 件は [DECISIONS.md](DECISIONS.md) に記録する。

## M1：盤面表現と SFEN

**目標**：SFEN 文字列から局面を作り、盤面を表示できる。

- `Bitboard`：`uint16_t` ラッパー、集合演算、`lsb`/`popcount`
- `Position`：盤配列、ビットボード、持ち駒、手番の保持
- SFEN のパースと生成
- ASCII 盤面表示
- CLI サブコマンド `show <sfen>`

**完了条件**：初期局面の SFEN を渡すと第 2.2 節の盤面が表示される。往復テストが通る。

**設計判断**：持ち駒の内部表現。
駒種ごとに 4 ビットずつ `uint16_t` に詰めるか、`uint8_t` の配列にするか。
枚数の増減、ゼロ判定、ハッシュ更新のどれを速くしたいかで選択が変わる。

## M2：利きと指し手生成

**目標**：合法手を列挙でき、perft が動く。

- `attack.hpp`：`constexpr` による利きテーブルの生成
- `is_attacked()`：あるマスが特定の手番から利きを受けているか
- 移動手の生成、打つ手の生成
- `do_move` / `undo_move` と `StateInfo`
- perft の実装と CLI サブコマンド `perft <depth>`

**完了条件**：perft(1) = 4 が一致し、深さ 5 程度まで参照実装と一致する。

**設計判断**：`is_attacked()` の実装方式。
駒種ごとに逆引きテーブル（そのマスへ利かせられる位置の集合）を引く方式と、相手の駒を走査して利きの和を取る方式がある。
どちらもテーブル引きで済むが、呼び出し頻度と分岐の数が違う。

このマイルストーンが本プロジェクトの中心である。
ここが正しく速ければ、以降はその上に載るだけになる。

## M3：規則の完成

**目標**：対局が最後まで進み、勝敗が付く。

- Zobrist ハッシュと差分更新
- 終局判定（キャッチ、トライ、千日手）
- 局面履歴の保持と繰り返し検出
- CLI サブコマンド `play`（人間同士、ランダム AI との対局）

**完了条件**：第 9.2 節の規則テストがすべて通る。CLI で初手から投了まで指せる。

**設計判断**：千日手の検出方法。
探索経路のハッシュ列を線形走査する方式は単純だが、探索が深くなると走査コストが効いてくる。
どこまで遡るか、何回目の出現で引き分けとするかを決める。

## M4：評価関数

**目標**：局面に点数が付く。

- 駒割、ライオン前進度、ライオン安全度の各項
- 評価値の符号規約（手番側から見た値に統一する）
- CLI サブコマンド `eval <sfen>`

**完了条件**：初期局面の評価値が 0 付近、明らかに優勢な局面で正の大きな値になる。

**設計判断**：評価項目の重み付けと、ライオン前進度の段別ボーナス表。
トライを狙う価値と、前に出たライオンが取られる危険をどう釣り合わせるか。
既存のブラウザ実装が持つ値（`LION_ADV = [0, 3, 20, 55]`）は一つの解でしかない。

ここは正解のない設計判断であり、後の自己対局で調整する対象になる。

## M5：探索

**目標**：それなりに強い着手を返す。

- αβ 探索（fail-soft）
- 反復深化
- 置換表
- move ordering（置換表の手、MVV-LVA、killer、history）
- 静止探索
- 時間管理
- CLI サブコマンド `go <sfen>`, `bench`

**完了条件**：3 手詰めの局面で正しい手を返す。深さを増やしても評価値が発散しない。

**設計判断**：move ordering の優先順位。
どうぶつしょうぎではトライ成立手とライオンへの王手が特別な意味を持つため、本将棋の定石をそのまま持ち込むのが最適とは限らない。

**設計判断**：静止探索で展開する手の範囲。
取る手だけでは、トライで決まる局面を見落とす可能性がある。

## M6：USI 層

**目標**：エンジンとして外から使える。

- USI コマンドの解釈と応答
- 探索スレッドの分離と `stop` の実装
- `info` の出力（depth, nodes, nps, score, pv）
- 外部エンジンのホスト機能（`UsiEngine`）
- CLI サブコマンド `usi`（エンジンモード）、`match`（エンジン同士の対局）

**完了条件**：自作エンジン 2 プロセスを対局させ、最後まで進む。

**設計判断**：時間制御の方針。
持ち時間から 1 手あたりの割り当てをどう決めるか。
どうぶつしょうぎは平均対局手数が短く、終盤の重要度が高い。

## M7 以降：解析（将来）

第 1 段階の完了後に着手する。

- **df-pn**：キャッチ／トライ必至の証明数探索。詰み探索の専用モジュール
- **完全解析**：後退解析による全局面の勝敗表。局面の密な索引付けが前提になる
- **定跡**：完全解析の結果から最短勝ち筋を抽出する
- **Python バインディング**：pybind11 による薄いラッパー。機械学習用途の入口

完全解析は 2.46 億局面を扱う。
1 局面 1 バイト（勝敗と手数）でも 250 MB 弱であり、索引付けの効率がそのままメモリ量に効く。
索引の設計は、駒ごとの位置を組み合わせ数で符号化する方式を検討する。

## 依存関係

```
M0 ──> M1 ──> M2 ──> M3 ──> M4 ──> M5 ──> M6
                      │              │
                      └──────────────┴──> M7
```

M4 と M5 は往復しながら進める。
探索が動かないと評価関数の良し悪しは測れず、評価関数がないと探索の効果も見えない。
先に M5 の骨格（置換表なしの素朴な αβ）を作り、M4 の評価と交互に改良する進め方でもよい。
