# どうぶつしょうぎライブラリ 仕様書

版：0.1（2026-08-06）

## 1. 目的とスコープ

本プロジェクトは、どうぶつしょうぎの局面表現、合法手生成、終局判定、探索を提供する C++ ライブラリと、その上に載る CLI ツールである。
設計の参照先は cshogi（高速な Python 将棋ライブラリ）であり、そこで確立している「ヘッダ中心の高速コア＋薄い外部インタフェース」という構造を、どうぶつしょうぎの規模に合わせて再構成する。

第 1 段階で作るもの：

- **コアライブラリ**：局面、指し手生成、SFEN 入出力、終局判定、Zobrist ハッシュ
- **探索**：αβ 探索、置換表、静止探索、評価関数
- **CLI**：局面表示、対局、指し手解析、ベンチマーク

将来の拡張として設計上の余地だけ確保しておくもの：

- **USI 層**：自作エンジンを USI 互換プロセスとして起動する機能と、外部 USI エンジンをホストする機能
- **完全解析データベース**：後退解析による全局面の勝敗表
- **df-pn**：キャッチ／トライ必至の証明数探索

第 1 段階で作らないもの：Python バインディング、GUI、ニューラルネットワーク評価関数。
ただし後から追加できるよう、コアライブラリは外部ライブラリに依存させない。

## 2. ゲームの規則

規則の記述は、機械が判定できる粒度まで落とす。
曖昧さが残る箇所（トライの成立条件、千日手の数え方）は、本節での定義を実装の正とする。

### 2.1 盤と駒

盤は 3 筋 4 段の 12 マスである。
駒は 5 種類あり、うち成駒が 1 種類ある。

- **ライオン** (L)：8 方向に 1 マス
- **きりん** (G)：上下左右に 1 マス
- **ぞう** (E)：斜め 4 方向に 1 マス
- **ひよこ** (C)：前に 1 マス
- **にわとり** (H)：ひよこの成駒。前、前斜め 2 方向、左右、後ろの 6 方向に 1 マス（後ろ斜めには動けない）

括弧内の英字を駒の識別子として全体で用いる[^piece-letter]。

[^piece-letter]: 本将棋の駒文字（P/L/N/S/G/B/R/K）と衝突しないよう、動物名の頭文字を採る。G は「ぎん」ではなく「きりん」である点に注意する。

### 2.2 初期配置

先手が下（d 段）、後手が上（a 段）に位置する。

```
   3   2   1
 +---+---+---+
 |きり|ライ|ぞう|  a  ← 後手
 +---+---+---+
 |   |ひよ|   |  b
 +---+---+---+
 |   |ヒヨ|   |  c
 +---+---+---+
 |ゾウ|ライ|キリ|  d  ← 先手
 +---+---+---+
```

先手から見て、左にぞう、中央にライオン、右にきりん、その手前にひよこが並ぶ。

### 2.3 着手

手番の側は、次のいずれかを行う。

- **移動**：自分の駒を、その駒の利き先のうち、自駒のないマスへ動かす。相手の駒があればそれを取る。
- **打つ**：持ち駒を空きマスに置く。

取った駒は持ち駒になり、次の手番以降に打てる。
にわとりを取った場合、持ち駒になるのはひよこである。
ライオンを取った時点で対局は終了するため、ライオンが持ち駒になることはない。

**成り**：ひよこが敵陣最奥段（先手なら a 段、後手なら d 段）に移動したとき、必ずにわとりに成る。
成らない選択肢はない。
打った駒は、たとえ最奥段に打っても成らない。
にわとりが敵陣に入っても何も起きない。

**禁じ手**：本将棋にある二歩、打ち歩詰め、行き所のない駒、連続王手の千日手に相当する反則は、どうぶつしょうぎには存在しない。
王手を放置する着手も反則ではない。
放置すれば次の手でライオンを取られて負けるだけである。

この一点が実装に与える影響は大きい。
擬似合法手と合法手が一致するため、自殺手の除去も pin の検出も不要になる。

### 2.4 終局

次のいずれかで対局は終了する。

- **キャッチ**：相手のライオンを取った側の勝ち。
- **トライ**：自分のライオンを敵陣最奥段（先手なら a 段、後手なら d 段）に移動させ、かつ移動先が相手のどの駒の利きも受けていないとき、その側の勝ち。
- **千日手**：同一局面が 3 回出現した時点で引き分け。

トライの判定は、**手番が回ってきた時点**で次の順に行う。

1. 手番側が相手のライオンを取れる（相手のライオンのマスに手番側の利きがある）なら、**手番側の勝ち**（キャッチ）
2. 1 でなく、相手のライオンが手番側の自陣最奥段（先手にとっては d 段、後手にとっては a 段）にいるなら、**手番側の負け**（トライ成立）
3. どちらでもなければ対局は続く

この定義は田中哲朗「どうぶつしょうぎの完全解析」に従う。
経緯と他実装との比較は [TRY_RULE.md](TRY_RULE.md) にまとめてある。

素のルールには「取れる位置にトライされたのに取らなかった場合」の規定がなく、
どうぶつしょうぎには反則がない（ライオン取らずも合法）ため、そのままでは勝敗が決まらない局面が生じる。
上の定義は「取れる状態そのものを終局とみなす」ことでこれを閉じる。
「取らない」という着手が存在しなくなるため、放置の問題が発生しない。

勝敗の結論は「最奥段に到達した瞬間に狙われていなければ勝ち」という読み方と一致する。

| ライオンが最奥段に到達した直後 | 結果 |
| --- | --- |
| 到達先が相手の利きを受けている | 相手の手番でキャッチが成立し、**動かした側の負け** |
| 到達先が相手の利きを受けていない | 相手の手番で 2 が成立し、**動かした側の勝ち** |

違いは、トライが成立しないまま対局が続く場合が存在しなくなる点にある。
ライオンが最奥段に着いた次の手番で必ず決着するため、
「最奥段に居座ったライオンが、後から相手の利きが外れて勝ちになる」という状態は生じない。

この判定は局面だけで決まり、そこへどう到達したかに依存しない。
置換表および完全解析データベースとの相性が良く、
`GameResult result() const` は直前の着手を引数に取る必要がない。

同一局面の判定に用いるのは、盤面の駒配置、両者の持ち駒、手番の 3 つである。
手数と過去の履歴は含めない。

キャッチとトライが同時に成立する着手（ライオンを最奥段に動かして相手ライオンを取る）は、キャッチとして扱う。
勝者は同じなので実害はないが、終局理由の記録が一意に定まる。

### 2.5 規模

田中哲朗による完全解析では、初期局面から到達可能な局面は 246,803,167 局面であり、双方最善で 78 手後手勝ちが結論である[^tanaka]。
1 局面あたりの平均合法手数は 9.435 である。

この数字は二つの意味を持つ。
第一に、探索エンジンの評価基準が明確である（完全解析と一致するかを直接検証できる）。
第二に、後退解析による完全解が現実的な計算量に収まる。

[^tanaka]: 田中哲朗「『どうぶつしょうぎ』の完全解析」情報処理学会研究報告, 2009. 後退解析により全局面を解いており、探索時間はパソコンで 5 時間半とされる。

## 3. 座標系と記法

### 3.1 座標系

USI に準じ、筋は右から 1, 2, 3、段は上から a, b, c, d とする。
マスは筋と段を並べて `2c` のように表す。
先手のライオンの初期位置は `2d`、後手のライオンは `2a` である。

内部表現では 12 マスに 0 から 11 の連番を振る。
段優先（`3a` = 0, `2a` = 1, `1a` = 2, `3b` = 3, ..., `1d` = 11）とし、a 段側を添字 0 に置く。
この順序は SFEN の文字列順と一致するため、変換が単純になる。

筋と段も、それぞれ 0 起点の内部値を持つ。
段は `a` から順に 0, 1, 2, 3 とし、筋は**左から** 0, 1, 2 とする。
すなわち内部値 0 が筋 3、内部値 2 が筋 1 に対応し、USI の筋番号とは向きが逆転する。
マスの連番は `段 × 3 + 筋` で得られる。

この逆転を許すのは、内部値を 0 起点に揃えて配列添字として直接使えるようにするためである。
向きの変換は文字列入出力の内部にのみ現れ、他の層からは 0 起点の座標系だけが見える。
列挙定数の名前は `FILE_3 = 0` のように USI 表記を保ち、対応を読み解けるようにする。

盤外を表す番兵 `SQ_NONE` の値は 15 とする。
第 5.3 節の指し手はマスを 4 ビットで保持するため、番兵も 4 ビットで表せる必要がある。

### 3.2 SFEN 方言

局面文字列は 4 つのフィールドからなる。

```
<盤面> <手番> <持ち駒> <手数>
```

初期局面は次のとおり。

```
gle/1c1/1C1/ELG b - 1
```

- **盤面**：a 段から d 段へ、各段は筋 3 から筋 1 へ。段の区切りは `/`。先手の駒は大文字、後手の駒は小文字。連続する空きマスは数字で表す。にわとりは `+C` および `+c` と書く。
- **手番**：先手は `b`、後手は `w`。
- **持ち駒**：先手の持ち駒を大文字、後手を小文字で `GECgec` の順に並べる。2 枚あるときは `2G` のように枚数を前置する。持ち駒がないときは `-`。
- **手数**：1 から始まる整数。

盤面フィールドの `+` 記法は本将棋の SFEN と同じ規則である。
どうぶつしょうぎの成駒はにわとり 1 種類のみなので、`+C` 以外の成駒表記は現れない。

### 3.3 指し手の記法

USI に準じる。

- **移動**：移動元と移動先を並べる。`2c2b`
- **成りを伴う移動**：末尾に `+` を付ける。`2b2a+`
- **打つ**：駒文字と `*` と打つ先。`C*2b`

ひよこの成りは強制なので、`+` の有無で指し手が分岐することはない。
それでも `+` を明記するのは、USI 互換の記法を保ち、棋譜を他のツールで読めるようにするためである。
入力を解釈する側は、成りが強制される着手について `+` の欠落を許容する。

### 3.4 日本語棋譜

CLI の表示および棋譜出力のために、`☗2二ひよこ` のような日本語表記を生成する。
段は漢数字（一〜四）、筋は算用数字を用いる。
同一の移動先へ複数の駒が動ける場合の曖昧性解消（「右」「左」「直」）は、盤が小さく駒種も少ないため、駒種名だけで一意に定まる場合がほとんどである。
一意に定まらない場合に限り、移動元を括弧書きで添える。

### 3.5 盤面の ASCII 表示

`Position::to_ascii()` が返す書式を次のように定める。初期局面の出力を示す。

```
  3   2   1
+---+---+---+
| g | l | e | a
+---+---+---+
|   | c |   | b
+---+---+---+
|   | C |   | c
+---+---+---+
| E | L | G | d
+---+---+---+
hand: -
turn: b
ply: 1
```

- **駒文字**：`L` `G` `E` `C` `H`（ライオン、キリン、ゾウ、ひよこ、にわとり）。先手は大文字、後手は小文字。空マスは空白。
- **にわとり**：SFEN と異なり `+C` ではなく 1 文字の `H` で表す。マスの幅が 1 文字だからである。
- **段のラベル**：各段の右に `a`〜`d` を置く。筋のラベルは先頭行に置く。
- **持ち駒**：`hand:` に続けて `駒文字*枚数` を空白区切りで並べる。順序は SFEN と同じく `GECgec`。持ち駒がないときは `-`。
- **手番**：`turn:` に続けて SFEN と同じ `b` / `w`。
- **手数**：`ply:` に続けて整数。
- 出力は改行で終わる。行末に余分な空白を置かない。

盤面だけでなく手番と手数まで含めるのは、この文字列が CLI 表示とデバッグの両方で
「局面の全情報」として読まれるためである。
手番の取り違えは指し手生成の誤りとして現れ、盤面だけを見ていると原因にたどり着けない。

にわとりの表記が SFEN と異なるため、この書式は解析の対象としない。
文字列から局面を復元する経路は SFEN のみとする。

## 5. データ表現

### 5.1 駒と手番

駒種は 0 から 5 の整数で表す。

```cpp
enum PieceType : uint8_t {
    NO_PIECE_TYPE = 0,
    LION = 1, GIRAFFE = 2, ELEPHANT = 3, CHICK = 4, HEN = 5,
    PIECE_TYPE_NB = 6
};

enum Color : uint8_t { BLACK = 0, WHITE = 1, COLOR_NB = 2 };
```

盤上の駒は、駒種と所有者を 1 バイトに詰める。
上位ビットに手番、下位に駒種を置く。

持ち駒は、きりん、ぞう、ひよこの 3 種類が各 2 枚まで。
手番ごとに `uint16_t` 1 個へ詰める（各駒種 2 ビット、余裕を見て 4 ビット確保）。

### 5.2 ビットボード

12 マスなので `uint16_t` で表現する。
ビット位置はマスの連番に対応させる。

```cpp
class Bitboard {
    uint16_t b_;   // bit i がマス i に対応
};
```

利きは事前計算したテーブルを引くだけで求まる。

```cpp
// attacks[駒種][手番][マス] -> そのマスから利くマスの集合
constexpr Bitboard PieceAttacks[PIECE_TYPE_NB][COLOR_NB][SQ_NB];
```

サイズは 6 × 2 × 12 × 2 バイト = 288 バイトであり、L1 キャッシュに常駐する。
テーブルは `constexpr` 関数でコンパイル時に生成し、実行時の初期化を不要にする。

飛び利きの駒が存在しないため、occupancy に依存する利き計算は一切現れない。
本将棋ライブラリの複雑さの大半を占める部分が、この設計では消える。

### 5.3 指し手

`uint16_t` に詰める。

| ビット | 内容 |
| --- | --- |
| 0-3 | 移動先マス（0-11） |
| 4-7 | 移動元マス（0-11）、打つ手では `SQ_NONE` = 15 |
| 8 | 成りフラグ |
| 9-11 | 打つ駒種、移動の手では `NO_PIECE_TYPE` = 0 |

打つ手であることは、移動元が `SQ_NONE` であることで表す。
独立した「打つ手フラグ」は置かない。フラグと駒種の 二重管理を避け、
どのアクセサもすべての指し手に対して意味のある値を返す状態を保つため（D-014）。

| | 移動の手 | 打つ手 |
| --- | --- | --- |
| `to_sq(m)` | 移動先 | 打つ先 |
| `from_sq(m)` | 移動元 | `SQ_NONE` |
| `dropped_piece(m)` | `NO_PIECE_TYPE` | 打つ駒種 |
| `is_promotion(m)` | 成るか | 常に `false` |

`Move` は生の整数ではなく `enum class Move : std::uint16_t` とする。
値 0 を `Move::NONE`（指し手なし）の番兵として予約する。
0 は「移動先 = 移動元 = `SQ_3A`」に対応し、`from == to` の指し手は存在しないため衝突しない。

探索の並び替えのため、指し手にスコアを添えた構造体を別に用意する。
指し手そのものを 16 ビットに保つのは、置換表のエントリを小さく保つためである。

### 5.4 局面

```cpp
class Position {
    Piece    board_[SQ_NB];      // マスごとの駒
    Bitboard byColor_[COLOR_NB]; // 手番ごとの駒の集合
    Bitboard byType_[PIECE_TYPE_NB];
    uint16_t hand_[COLOR_NB];    // 持ち駒。1 駒種 2 ビット、片側 6 ビット
    Color    sideToMove_;
    uint16_t ply_;
    Key      key_;               // Zobrist ハッシュ
};
```

盤配列とビットボードを両方持つのは冗長だが、駒の取得（配列）と集合演算（ビットボード）の双方が頻出するため、更新コストを払っても引き算が速いほうを選ぶ。

**着手の適用と巻き戻し**：`do_move` / `undo_move` の対で実装する。
巻き戻しに必要な情報（取った駒、更新前のハッシュ）は `StateInfo` に退避し、探索側がスタックとして保持する。
局面のコピーは行わない。

### 5.5 Zobrist ハッシュ

64 ビットのハッシュを用いる。
乱数の割り当ては、盤上の駒（駒種 × 手番 × マス）、持ち駒（駒種 × 手番 × 枚数）、手番の 3 系統。

千日手判定は、探索経路上のハッシュ列を線形に走査して同一値を数える。
盤が小さく探索も浅いため、専用のハッシュテーブルは持たない。

ハッシュ衝突による誤判定を避けるため、千日手が疑われる局面では盤面の完全一致も確認する。

### 5.6 局面のパック表現

置換表の検証と、将来の完全解析データベースのために、局面を 64 ビット未満へ可逆に詰める表現を定義する。
各マス 4 ビット（駒種 3 ビット＋所有者 1 ビット）で 12 マス分 48 ビット、持ち駒 12 ビット、手番 1 ビットの計 61 ビットに収まる。

この表現は空間効率が最適ではない（到達可能局面は 2.5 億弱なので、理論的には 28 ビットで足りる）。
完全解析に着手する段階で、駒ごとの位置を割り当てる密な索引付けへ差し替える。
第 1 段階では、正しさの検証に使える単純な表現を優先する。

## 6. API

### 6.1 局面

```cpp
class Position {
public:
    static std::optional<Position> from_sfen(std::string_view sfen);
    static Position startpos();

    std::string sfen() const;

    Color  side_to_move() const;
    Piece  piece_on(Square s) const;
    int    hand_count(Color c, PieceType pt) const;
    Key    key() const;
    int    ply() const;

    void do_move(Move m, StateInfo& st);
    void undo_move(Move m);

    bool is_consistent() const;       // 内部表現の整合性（常に真であるべき不変条件）
    bool is_legal_position() const;   // 局面としての妥当性（駒数、ライオンの枚数）

    bool is_attacked(Square s, Color by) const;
    Square lion_square(Color c) const;

    // 終局判定。手番が回ってきた局面に対して呼ぶ（第 2.4 節）
    GameResult result() const;

    std::string to_ascii() const;   // CLI 表示用
};
```

`GameResult` は、継続、キャッチ勝ち、トライ勝ち、千日手引き分けを区別する列挙型とする。
勝者は別に返す。

`StateInfo` は、着手を戻すために必要な情報のうち、`Move` から復元できないものを持つ。

```cpp
struct StateInfo {
    Piece      captured;   // 取った駒。取っていなければ NO_PIECE
    StateInfo* previous;   // 1 手前の StateInfo
};
```

`Position` は現在の `StateInfo` へのポインタを保持する。
`do_move()` が鎖に繋ぎ、`undo_move()` が 1 つ戻す。
千日手判定はこの鎖を遡って行う（M3）。

`StateInfo` の寿命は呼び出し側が管理する。
探索では深さぶんの配列を確保し、`pos.do_move(m, stack[ply])` の形で使う。
`Position` をコピーすると `StateInfo` へのポインタも複写されるため、
コピー後に `undo_move()` を呼んではならない。

`do_move()` は着手が合法であることを前提とし、検査しない（D-009 と同じ契約）。

## 7. 評価関数と探索

### 7.1 評価関数

第 1 段階では、手作りの線形評価を用いる。

- **駒割**：ひよこ、ぞう、きりん、にわとりに点数を与える。盤上の駒と持ち駒で係数を変える。
- **ライオンの前進度**：トライが勝ち筋である以上、ライオンが敵陣に近いことは価値を持つ。段ごとのボーナス表を持つ。
- **ライオン周辺の安全度**：自ライオンの隣接マスが相手の利きを受けている数に対する減点。
- **駒の可動域**：利きの数。盤が狭いため寄与は小さいと見込まれる。

既存のブラウザ実装（`dobutsu-shogi.html`）が持つ評価値は、初期パラメータの出発点として使える。

### 7.2 探索

- 反復深化
- 置換表（局面ハッシュ、深さ、評価値、種別、最善手）
- move ordering：置換表の手、取る手（MVV-LVA）、killer move、history
- 静止探索：取る手とトライ成立手のみを展開
- null move pruning は導入しない。盤が狭く zugzwang が頻出すると見込まれるため、効果より危険が大きい。

終局判定は探索の内部でも必要になる。
キャッチとトライは着手適用後に即座に判定でき、いずれも探索を打ち切る。
千日手は探索経路上での繰り返しを検出し、評価値 0 を返す。

**詰みスコアの扱い**：勝敗が確定した局面の評価値は、`MATE - ply` の形で手数を織り込む。
これにより、同じ勝ちでも短い勝ち筋が選ばれる。

## 9. テスト戦略

### 9.1 perft

指し手生成の正しさは perft（深さ n までの葉ノード数）で検証する。
既知の外部データが存在しないため、次の手順で基準値を確定させる。

1. 初期局面の perft(1) = 4 を手計算で確認する（ひよこ 1 手、ライオン 2 手、きりん 1 手、ぞうは動けない）。
2. 深さ 2 以降を実装で算出し、独立に書いた素朴な実装（配列ベースの参照実装）と突き合わせる。
3. 一致した値を回帰テストの基準として固定する。

終局する枝の扱いを明確にする。
終局した局面は葉として数え、その先は展開しない。
判定は第 2.4 節のとおりノードの入口で 1 回行う。
着手を適用した直後に調べるのではなく、次のノードに入った時点で調べる形になる。

```cpp
std::uint64_t perft(Position& pos, int depth){
    if(is_terminal(pos)) return 1;
    if(depth == 0) return 1;
    ...
}
```

この規則では、実際にライオンが盤上から取り除かれる局面には到達しない。
取れる状態が現れた時点で終局するためである。
千日手は perft では考慮しない（同一局面の再訪も別の葉として数える）。

最終的な整合性の確認として、全到達局面の列挙が 246,803,167 になることを検証する。
これは幅優先探索で到達可能な局面を数え上げる別のテストとして用意する。

### 9.2 規則のテスト

境界条件を個別に検証する。

- ひよこが最奥段に到達して成る／打ったひよこは成らない
- にわとりを取ると持ち駒はひよこになる
- トライ成立（利きなし）とトライ不成立（利きあり）
- キャッチとトライが同時に成立する着手
- 王手放置が合法手として生成される
- 同一局面 3 回で引き分け

### 9.3 SFEN の往復テスト

局面 → SFEN → 局面 の変換が恒等になることを、ランダム生成した局面で検証する。
指し手についても USI 記法との往復を確認する。

往復テストだけでは不十分である。
`sfen()` と `from_sfen()` が打ち消し合う誤りを持つ場合、往復は成立するのに両方が間違っている。
次の 3 種類を組み合わせる。

1. **固定文字列との照合**（片側だけの検証）
   `Position::startpos().sfen()` が `gle/1c1/1C1/ELG b - 1` に一致すること。
   `from_sfen()` を経由しないため、往復テストの対称性を破る錨になる。
2. **往復**
   正規形の SFEN 文字列に対して `from_sfen(s)->sfen() == s`。
   `from_sfen()` は非正規形（`GG`、余分な空白）も受け付けるが、`sfen()` は必ず正規形を返すため、
   往復テストの入力は正規形に限る。
3. **内容の直接確認**
   `from_sfen()` の結果に対し `piece_on()` / `hand_count()` / `side_to_move()` / `ply()` /
   `pieces(PieceType)` を個別に検証する。特に `pieces(HEN)` は往復テストからは観測できない。

### 9.3.1 異常系テストの独立性

`from_sfen()` が拒否すべき入力は、**拒否理由ごとに 1 つずつ**用意する。
1 つの入力が複数の理由で拒否されると、そのうち 1 つの検査を削除してもテストが落ちないため、
検査の存在を保証できない。

拒否理由の一覧（各行に対して、他の理由では拒否されない入力を用意する）。

| 理由 | 例 |
|---|---|
| フィールド数が 4 でない | `gle/1c1/1C1/ELG b -` |
| 盤面の駒文字が不正 | `xle/1c1/1C1/ELG b - 1` |
| 段の区切り位置が不正 | `gle/1c2/1C1/ELG b - 1` |
| 段数が 4 でない | `gle33ELG b Cc 1`（マス数は 12 ちょうど） |
| 盤面のマス数が 12 を超える | `gle/1c1/1C1/ELGG b - 1` |
| `+` の直後が ひよこ でない | `gle/1c1/1+H1/ELG b - 1`（他の理由では拒否されない） |
| 手番が `b` / `w` でない | `gle/1c1/1C1/ELG x - 1` |
| 持ち駒に置けない駒種 | `gle/1c1/1C1/E1G b L 1` |
| 持ち駒が 1 駒種 3 枚以上 | `glG/1c1/1C1/EL1 b 2G2G 1` |
| 駒種ごとの総数が 2 でない | `gle/1c1/1Cc/ELG w - 1` |
| ライオンが各手番 1 枚でない | `g1e/1c1/1CL/ELG b - 1` |
| 手数が 0 以下 | `gle/1c1/1C1/ELG b - 0` |
| 手数が `uint16_t` の範囲外 | `gle/1c1/1C1/ELG b - 70000` |
| 手数に数値以外が混じる | `gle/1c1/1C1/ELG b - 12abc` |

### 9.4 テストの検証（突然変異テスト）

テストが実際に何かを保証しているかは、**実装をわざと壊してテストが落ちるか**で確認する。
検査を 1 つ削る、比較演算子を反転する、定数を変える、といった変更を加えてテストを走らせ、
落ちなければそのテストはその箇所を検証していない。
`to_ascii()` のように分岐を持つ出力関数では、分岐ごとに入力を用意しないと大半が未検証のまま残る。

なお、テストでは原理的に殺せない突然変異が存在する。次の 2 つはその例で、追加のテストでは対処できない。

- **範囲外書き込みの境界**（`from_sfen()` の `sq_idx >= SQ_NB` を `>` にする）
  どちらでも `std::nullopt` を返し、違いは配列外に書くかどうかだけである。
  検出には AddressSanitizer のような実行時検査が要る。
- **将来のための防御的検査**（`is_consistent()` の `byType_[HEN]` の比較）
  現状 `Position` を変更する経路は `put_piece()` しかなく、そこが正しい限り観測可能な差が出ない。
  `do_move()`（M2 以降）が入ると殺せるようになる。

これらは「テストが足りない」のではなく「今の設計では観測できない」ものとして区別する。

### 9.5 探索の検証

完全解析の結論との照合を最終的な正しさの基準とする。
第 1 段階では、既知の詰み局面で正しい手数の詰みを見つけるか、深さを増やしたときに評価値が振動せず収束するかを確認する。
