# 設計判断の記録

仕様書：[SPEC.md](SPEC.md) ／ ロードマップ：[ROADMAP.md](ROADMAP.md)

SPEC.md が「何を作るか」を定めるのに対し、本書は「なぜそう決めたか」を残す。
後から読んだときに、決定を覆してよいか（前提が変わったか）を判断できることを目的とする。

各項目には、決定・理由・帰結を記す。
帰結の欄には、その決定が壊れたときに何が起きるかを書く。

## M0：土台

### D-001　`Piece` は上位ビットに手番を置く

**決定**：1 バイトのうち bit3 を手番、bit0-2 を駒種とする。
`NO_PIECE = 0`、先手の駒が 1〜5、後手の駒が 9〜13、`PIECE_NB = 16`。

**理由**：`type_of()` がマスク 1 回、`color_of()` がシフト 1 回で済む。
手番ごとに値が連続するため、`Piece` を添字とするテーブルで「手番込みの駒」を直接引ける。
Stockfish および cshogi の慣行と一致するため、両者のコードを参照する際の読み替えが不要になる。

**帰結**：値 6, 7, 14, 15 が欠番となり、`Piece` を添字とする配列は 16 要素のうち 4 要素が無駄になる。
これは意図的な浪費である。
値を 12 個に詰めると `make_piece()` が乗算になり、さらに 16 という 2 の冪を失うことでアドレス計算からシフト最適化が消える。
M2 で作る利きテーブルは 288 バイトであり、数十バイトの無駄より計算の単純さが勝つ。

ビット配置を知るコードは `make_piece()` / `type_of()` / `color_of()` の 3 関数に限定する。
定数 `COLOR_SHIFT` と `PT_MASK` を経由させ、他の場所にビット幅の知識を漏らさない。

### D-002　筋と段の内部値は 0 起点とし、定数名で USI 表記を保つ

**決定**：`FILE_3 = 0, FILE_2 = 1, FILE_1 = 2` および `RANK_A = 0, ..., RANK_D = 3` とする。
マスの連番は `段 × 3 + 筋`。

**理由**：内部値を 0 起点に揃えれば配列添字にそのまま使える。
筋については、USI の筋番号が右から 1, 2, 3 であるのに対し内部値は左から 0, 1, 2 となり、対応が逆転する。
この逆転を `square_to_usi()` / `square_from_usi()` の 2 関数だけに閉じ込め、それ以外のコードからは 0 起点の素直な座標系だけが見えるようにする。

定数名を `FILE_3` のままにするのは、`FILE_3 = 0` という一見ねじれた対応を、名前の側で読み解けるようにするためである。

**帰結**：`'3' - 内部値` という変換が現れるのは文字列変換の内部だけである。
他のファイルにこの計算が漏れたら、座標系の設計が崩れたサインとみなす。

### D-003　番兵 `SQ_NONE` の値は 15

**決定**：`SQ_NB = 12` と別に `SQ_NONE = 15` を定義する。

**理由**：SPEC 5.3 により、`Move` はマスを 4 ビットのフィールドに格納する。
番兵が 4 ビットで表せる値であれば、`Move` の中に `SQ_NONE` をそのまま置ける。

**帰結**：この値はバイナリ表現の一部であり、後から変更すると `Move` の互換性が失われる。
M0 の時点で確定させたのはこのためである。

### D-004　変換関数は例外を投げず、番兵を返す

**決定**：`square_from_usi()` は不正な入力に対して `SQ_NONE` を返す。
`square_to_usi()` は盤外のマスに対して空文字列を返す。
SPEC 6.4 の指し手解釈と同じ方針である。

**理由**：これらの関数は SFEN や USI コマンドの解釈で使われる。
外部入力の不正は例外的事態ではなく想定内の事象であり、呼び出し側は必ず失敗を扱う必要がある。
例外にすると、探索から呼ばれる経路で例外処理のコストを負う可能性も残る。

**帰結**：呼び出し側は戻り値の検査を怠ってはならない。
検査漏れは `SQ_NONE` が盤の座標として流れ込む形で顕在化する。

### D-005　列挙型は `enum class` ではなく素の `enum` を使う

**決定**：`Color`, `PieceType`, `Piece`, `File`, `Rank`, `Square` はすべて素の `enum` とし、基底型に `std::uint8_t` を明示する。

**理由**：`enum class` は暗黙の整数変換を禁じるため型安全だが、`attacks[pt][c][sq]` のような添字アクセスのたびに `static_cast` が必要になる。
コアの中心となる指し手生成が添字操作の塊であることを考えると、可読性の損失が型安全性の利得を上回る。

基底型の明示は性能目標に直結する。
省略すると処理系は `int` を選び、`Piece board_[12]` が 12 バイトから 48 バイトへ膨らむ。
SPEC 10 節の「局面のメモリ 64 バイト以内」はこの指定に依存している。

**帰結**：型の取り違え（`PieceType` を `Piece` として渡すなど）をコンパイラが検出しない。
引数名の規約（`PieceType` は `pt`、`Piece` は `pc`、`Square` は `s`）でこれを補う。

なお素の `enum` であっても、演算結果は整数昇格により `int` になる。
enum 型を返す関数では明示的なキャストが必要である。

### D-006　ビルド構成は 3 ターゲット

**決定**：`dobutsu_core`（静的ライブラリ）、`dobutsu_cli`（実行ファイル）、`dobutsu_tests`（テスト）に分ける。
ヘッダ検索パスと C++20 要求は `dobutsu_core` に `PUBLIC` で付け、利用側へ伝播させる。

**理由**：コアを CLI から独立させることで、SPEC 8 節の USI 層や将来の Python バインディングを、CLI を巻き込まずに追加できる。
「コアは標準ライブラリ以外に依存しない」という制約が、ターゲットの依存グラフとして表現される。

**帰結**：GoogleTest への依存は `dobutsu_tests` だけが持つ。
`DOBUTSU_BUILD_TESTS=OFF` にすれば、ネットワーク接続なしでコアと CLI をビルドできる。

## M1：盤面表現と SFEN

### D-007　`Bitboard` は `uint16_t` の型別名ではなくクラスにする

**決定**：`using Bitboard = std::uint16_t;` ではなく、`std::uint16_t` を 1 個だけ持つクラスとして定義する。
集合演算は演算子オーバーロードで提供する。

**理由**：型別名にすると、`Bitboard` と「駒の枚数」と「マスの連番」がすべて同じ型になる。
ビットボードは添字ではなく値として関数間を渡り歩くため、引数の取り違えをコンパイラに検出させる価値が高い。

D-005 で `enum class` を退けた判断と方向が逆に見えるが、対象の性質が異なる。
`Square` や `PieceType` は配列の添字として使うことが主目的であり、暗黙変換の禁止が直接コストになる。
`Bitboard` は添字にならないため、そのコストが発生しない。

**帰結**：クラスにしたことで、`sizeof(Bitboard) == 2` が設計上の要件になる。
メンバに非 static な定数を持たせるとサイズが倍になり、SPEC 10 節の局面サイズ制約に波及する。
盤マスクの類は必ず `static constexpr` とすること。

### D-008　上位 4 ビットは常に 0 とし、不変条件を破れる箇所でのみマスクする

**決定**：`uint16_t` 16 ビットのうち bit12-15 は常に 0 に保つ。
盤マスク `0x0FFF` を掛けるのは `explicit Bitboard(std::uint16_t)` の 1 箇所のみとし、
補集合 `operator~` はその コンストラクタを経由して結果を構築する。

**理由**：`popcount()` は集合の要素数を返す契約であり、盤外のビットが混ざると値が狂う。
一方で `&` や `|` は両辺が不変条件を満たしていれば結果も満たすため、マスクは不要である。
全メソッドで防御的にマスクすると、指し手生成のホットパスに無駄な AND が並ぶ。

**帰結**：不変条件を知るコードは コンストラクタ 1 箇所に閉じる。
新たに `uint16_t` から `Bitboard` を作る経路を増やす場合は、必ずこのコンストラクタを通すこと。

### D-009　`lsb()` と `set()` / `reset()` は引数の妥当性を検査しない

**決定**：`lsb()` および `pop_lsb()` は集合が空でないことを、
`set()` / `reset()` / `test()` は `is_ok(s)` が真であることを、呼び出し側の責任とする。

**理由**：これらは M2 の指し手生成の最内周から呼ばれる。
D-004 で文字列変換に番兵方式を採ったのと異なり、ここでは不正な入力は外部からではなく実装の誤りとしてのみ発生する。
実行時に検査しても、返せる意味のある値が無い。

**帰結**：`square_from_usi()` が返した `SQ_NONE` を検査せずに `set()` へ渡すと、
bit15 が立って `popcount()` が実在しないマスを数える。
症状はビットボードの要素数の狂いとして、原因から離れた場所に現れる。
外部入力に由来する `Square` は、ビットボードに触れる前に検査すること。

### D-010　持ち駒は 1 駒種 2 ビット、片側 6 ビットに詰める

**決定**：`std::uint16_t hand_[COLOR_NB]` の下位 6 ビットを使う。
bit0-1 にきりん、bit2-3 にぞう、bit4-5 にひよこの枚数を置く。
上位 10 ビットは常に 0 とする。

駒種からシフト量への対応は `constexpr` の表で与え、`(pt - GIRAFFE) * 2` のような算術で導かない。

**理由**：持ち駒になりうるのはきりん・ぞう・ひよこの 3 種だけである。
ライオンは取られた時点で対局が終わるため持ち駒にならず、にわとりは取られるとひよこに戻る。
各駒種は盤上に 2 枚しか存在しないため、枚数の上限は 2 であり 2 ビットで表せる。

この配置は SPEC 5.6 のパック表現（持ち駒 12 ビット）とビット幅が一致する。
`hand_[BLACK] | (hand_[WHITE] << 6)` の連結だけでパックでき、詰め直しの変換関数が不要になる。

「持ち駒が 1 枚もない」の判定が `hand_[c] == 0` の 1 比較で済む点も、配列表現に対する利点である。
SFEN 生成と M3 のハッシュ更新で頻出する。

**帰結**：枚数の上限 2 に対して 2 ビットは 0〜3 を表せるため、余裕は 1 段しかない。
規則違反の局面（同じ駒種が 3 枚以上）を作ると隣の駒種のフィールドを侵食する。
SFEN 解析は枚数の妥当性を検査してから格納すること。

シフト量を算術で導かないのは D-001 と同じ理由による。
`GIRAFFE = 2` という `PieceType` の値と、持ち駒フィールドの並び順は、たまたま一致しているだけの別概念である。

### D-011　盤配列とビットボードの更新は 2 つの private 関数に集約する

**決定**：`board_` / `byColor_` / `byType_` を書き換える操作は `put_piece()` と `remove_piece()` の 2 つだけとし、
どちらも 3 者を同時に更新する。他のメンバ関数はこの 2 つを経由する。

**理由**：SPEC 5.4 は同じ情報を配列とビットボードの両方に持つことを定めている。
冗長性そのものは意図した取引だが、更新箇所が散らばると 3 者の同期が崩れる。
D-008 で不変条件を守る箇所をコンストラクタ 1 つに閉じたのと同じ構造を、ここでも作る。

**帰結**：同期の崩れは、盤面表示は正常なのに指し手生成だけが誤る、という形で現れる。
症状が原因から遠いため、整合性を検査する関数を用意し、テストから呼ぶ。
検査は「`board_` を走査して構築したビットボードが `byColor_` / `byType_` と一致するか」で足りる。

### D-012　`from_sfen()` は `std::optional<Position>` を返す

**決定**：SFEN の解析に失敗した場合、`std::nullopt` を返す。例外は投げない。

**理由**：D-004 および SPEC 6.4 と同じ方針である。
外部入力の不正は想定内の事象であり、呼び出し側は必ず失敗を扱う必要がある。

`Square` と異なり `Position` には番兵として使える値がない。
「空の局面」を失敗値に流用すると、正当な空盤面と区別できなくなる。
`std::optional` は失敗の可能性を戻り値の型として表現するため、検査漏れがコンパイル時に検出される。

**帰結**：SPEC 6.1 の宣言を `static std::optional<Position> from_sfen(std::string_view)` に改める。
コアライブラリの標準ライブラリ以外への非依存は保たれる。

### D-013　`to_ascii()` は SFEN と別の表記を持ち、解析の対象としない

**決定**：ASCII 表示ではにわとりを `H` の 1 文字で表し、持ち駒・手番・手数にラベルを付ける（SPEC 3.5）。
この書式を読み戻す関数は用意しない。

**理由**：盤面のマスは 1 文字幅なので、SFEN の `+C` をそのまま置くと桁が揃わない。
表示は人が読むためのもので、揃った格子であることが可読性の大半を占める。

持ち駒に `hand:` のラベルを付けるのは、持ち駒がないときの空行と、
表示の不具合で消えた場合とを区別できるようにするためである。
手番と手数を含めるのは、この文字列がデバッグ時に「局面の全情報」として読まれるためで、
手番の取り違えは指し手生成の誤りという遠い症状として現れる。

**帰結**：文字列から局面を復元する経路は SFEN 1 本に保たれる。
往復テスト（SPEC 9.3）の対象は `sfen()` と `from_sfen()` だけであり、
`to_ascii()` は出力を固定文字列と比較する形で検証する。

表示書式を変えるとそのテストが落ちる。これは意図した挙動で、
表示は仕様であり実装の都合で動かしてよいものではない、という位置づけを保つ。

## M2：利きと指し手生成

### D-014　打つ手は「移動元が `SQ_NONE`」で表し、専用フラグを置かない

**決定**：`Move` を `enum class Move : std::uint16_t` とし、ビット 0-3 に移動先、4-7 に移動元、
8 に成りフラグ、9-11 に打つ駒種を置く（SPEC 5.3）。
打つ手では移動元に `SQ_NONE`（= 15）を入れ、独立した「打つ手フラグ」は設けない。

**理由**：当初案は「打つ手フラグ」と「打つ駒種」を独立に持っていた。
この 2 つは互いに導出できるため、フラグが立っているのに駒種が 0、という不整合な値が作れてしまう。
また移動元欄が打つ手では未定義になるので、`from_sq()` を呼ぶ前に `is_drop()` を見なければならない、
という暗黙の契約が生まれる。

`SQ_NONE` を 15 にしてあることで、4 ビットのマス欄に「マスではない」を表す値がちょうど収まる。
これを使うと、どのアクセサもすべての指し手に対して意味のある値を返すようになり、
呼ぶ順番の制約が消える。

ビット数は 13 から 12 に減るが、それは選定理由ではない。
どうぶつしょうぎではマスが 12 通りしかなく、どの案でも `uint16_t` 1 個に収まるため、
ビット数は実用上の差を生まない。判断基準は「壊れた値を作れるか」に置いた。

`enum class` を選んだのは、`Move` が `Square` や `Piece` と混同されやすい位置にあり、
かつ整数として演算する必要がないためである。
`Piece` と `PieceType` を比較して警告だけで通った事故が実際に起きており、
新しく増える型については型どうしの取り違えをコンパイルエラーにする。

**帰結**：`is_drop(m)` は `from_sq(m) == SQ_NONE` として定義する。
`Move::NONE`（値 0）は「移動先 = 移動元 = `SQ_3A`」であり、`from == to` の指し手は存在しないため番兵に使える。

`Move` にスコアや取った駒は含めない。
置換表のエントリを小さく保つためであり、取った駒は `undo_move()` のために別途 `StateInfo` に積む。

### D-015　`move_from_usi()` は局面を参照せず、文字列どおりに変換する

**決定**：`move_from_usi()` は USI 文字列をビット列に変換するだけとし、成りの補正を行わない。

**理由**：ひよこの成りは強制なので、`2b2a` と `2b2a+` は同じ指し手を意味する（SPEC 3.6）。
しかし成るかどうかは移動先の段と駒種で決まるため、局面を知らない関数には判定できない。
局面を引数に取らせると、文字列変換の層が局面に依存してしまい、SPEC 4 の一方向の依存関係が崩れる。

**帰結**：`+` が省略された入力の解釈は、合法手リストと突き合わせる側（USI 層、M6）の責任とする。
成りフラグを無視して照合し、一致が 1 つに定まればその手を採用する。
どうぶつしょうぎでは成りが強制で選択の余地がないため、この照合は必ず一意に定まる。

ただし `from == to` は局面を参照せずに判定できる（規則ではなく構文の問題である）ため、
`move_from_usi()` の側で `Move::NONE` として弾く。
これを弾かないと、`3a3a` だけがビット列として `Move::NONE` と一致するために不正と判定され、
`2b2b` は有効な指し手として返る、という不整合が生じる。
番兵を置くときは、番兵と同じビット列を作れる入口をすべて塞ぐところまでを 1 組とする。

### D-016　整合性の検査を「内部不変条件」と「局面の妥当性」に分ける

**決定**：`is_consistent()` は `board_` とビットボードの一致だけを見る。
駒種ごとの総数が 2 であること、ライオンが各手番 1 枚であることは `is_legal_position()` に分離する。
`from_sfen()` は両方を要求し、`do_move()` の後は `is_consistent()` だけが成立する。

**理由**：どうぶつしょうぎではライオンを取る手が合法手として生成される（王手放置も合法、SPEC 9.2）。
したがって `do_move()` は盤上のライオンが 1 枚しかない局面を作る。これは終局した正当な局面である。

M1 の時点では、`Position` を作る経路が `from_sfen()` と `startpos()` しかなく、
そこでは 2 つの性質が常に同時に成立していたため、1 つの関数にまとめて差し支えなかった。
`do_move()` が入ると初めて食い違う。

内部不変条件は「実装がバグっていないか」を問い、局面の妥当性は「規則として存在しうる局面か」を問う。
前者はどんな局面でも常に真でなければならず、後者は局面によって偽になりうる。
問いの種類が違うものを 1 つの関数で答えると、どちらの意味で偽なのかが呼び出し側に伝わらない。

**帰結**：探索中の局面に対しては `is_consistent()` だけを検査する。
`is_legal_position()` は SFEN の入力検証と、テストで初期局面まわりを確かめるときに使う。

取ったライオンは持ち駒に加えない。
`HAND_SHIFT` はライオンに固有のビット位置を持たず（きりんと同じ 0）、
`add_hand(c, LION)` を呼ぶと きりん の枚数が増えてしまう。
ライオンは打てない駒なので持ち駒として表現する必要がなく、`do_move()` 側で除外する。

### D-017　`StateInfo` を鎖状に繋ぎ、`Position` が現在位置を保持する

**決定**：`StateInfo` に「取った駒」と「1 手前の `StateInfo`」を持たせ、
`Position` は現在の `StateInfo` へのポインタを保持する（SPEC 6.1）。
`do_move(Move, StateInfo&)` が鎖に繋ぎ、`undo_move(Move)` が 1 つ戻す。

**理由**：`undo_move()` は「何を取ったか」を知る必要があるが、`Move` には入っていない（D-014）。
置き場所の候補は 3 つあり、それぞれ別の代償を持つ。

- `Move` に入れる → 置換表のエントリが太る
- `Position` に履歴として持つ → 局面のコピーが重くなり、`Position` が値として扱いにくくなる
- 外に置く → `do_move` と `undo_move` の対応付けを呼び出し側が間違えられる

3 番目を選んだうえで、`Position` に「今どれか」だけを持たせて対応付けの誤りを防ぐ。
`StateInfo` を鎖にするのは、千日手判定（M3）で同一局面の履歴を遡る必要があるためで、
そのときに別の履歴構造を用意せずに済む。

**帰結**：`StateInfo` の寿命は呼び出し側が管理する。
探索では深さぶんの配列を確保する。
`Position` をコピーすると `StateInfo` へのポインタも複写されるため、
コピーした側で `undo_move()` を呼ぶと他方の鎖を壊す。局面のコピーは慎重に扱う。

### D-018　`MAX_MOVES` はゆるい上界のまま使う

**決定**：`MoveList` の配列長を、証明できる上界で決める。厳密な最大値には詰めない。
上界の根拠と、それがゆるいことをヘッダのコメントに残す。

**理由**：`Move` は 2 バイトなので、配列長を 40 から 128 に増やしても `MoveList` 1 個で 176 バイトしか変わらない。
探索の深さぶん積んでも数キロバイトであり、スタックに対して無視できる。
配列長を切り詰めても探索は速くならない（速度を決めるのは実際に生成された手の数）。

一方、上界が間違っていると配列外書き込みになり、テストからは見えない壊れ方をする。
したがって「たぶん足りる」ではなく「足りることが説明できる」必要がある。
説明できる範囲でゆるく取るのが、労力と安全性の釣り合う点である。

**帰結**：`add()` に `assert(size_ < MAX_MOVES)` を置き、上界の見積もりが誤っていた場合に静かに壊れるのではなく停止させる。
実測値が出たら上界と併記し、安全余裕がどれだけあるかを記録する。

**追記(実測結果)**: 実測値は、深さ 9 までに到達した範囲で 34、深さ 10 で 35、深さ 11 で 36 であった。深さを増やすごとに値が増え続けており収束していない。従って、これらは実際の最大値ではなく下界である。
ゆるい上界は 86 であり、2 倍程度の余裕があることを確認した。
なおコード上の上界は上記の通り変えないこととする。

### D-019　トライは田中方式で閉じる（終局判定に置き、指し手生成には入れない）

**決定**：トライとキャッチの判定を、手番が回ってきた時点で行う（SPEC 2.4）。
「相手のライオンを取れるなら手番側の勝ち、そうでなく相手のライオンが自陣最奥段にいれば手番側の負け」とする。
`MoveList` は変更しない。

**理由**：どうぶつしょうぎの公式ルールには「取れる位置にトライされたのに取らなかった場合」の規定がない。
反則が存在せず、ライオンを取らない着手も合法であるため、そのままでは勝敗が決まらない局面が生じる。
調査の詳細は [TRY_RULE.md](TRY_RULE.md) にある。

既存の実装は 3 通りの閉じ方をしている。

| 実装 | 閉じ方 | 変更する場所 |
| --- | --- | --- |
| 公式アプリ | 取られる位置へのトライを非合法手にする | 指し手生成 |
| どうぶつしょうぎウォーズ | 「取らない」着手を禁止する | 指し手生成 |
| 田中（完全解析） | 守備側の手番が来た時点で勝敗が確定する | 終局判定 |

田中方式を採る理由は 2 つある。

第一に、SPEC 9.1 で検証に使う「全到達局面 246,803,167」は田中論文の値である。
規則が違えば到達可能な局面の集合が変わるため、他の閉じ方を採るとこの照合が使えなくなる。
M7 の完全解析まで見据えると、規則を田中に合わせておく価値が大きい。

第二に、田中方式だけが指し手生成の外側で閉じている。
指し手生成に規則を入れると `MoveList` の意味が「盤上でどう動かせるか」から
「規則が強制した後に残る手」に変わり、perft が生成器の網羅性を測る道具でなくなる。
SPEC 4 の層の依存（`movegen` は終局規則を知らない）も崩れる。

**帰結**：終局判定が局面だけで決まるようになり、直前の着手に依存しなくなる。
`GameResult result(Move lastMove) const` は `GameResult result() const` に変更する。
置換表および完全解析データベースとの相性が良くなる。

副次的に、ライオンが盤上から取り除かれた局面には到達しなくなる。
`lion_square()` の「盤上にライオンがいること」という契約が、通常の対局では自動的に守られる。
ただし `do_move()` はライオンを取る着手を引き続き正しく処理する（`is_legal_position()` が偽になる局面として表現できる）。

### D-020　Zobrist の乱数表はコンパイル時に生成する

**決定**：`constexpr` な擬似乱数生成器（splitmix64）を自作し、`zobrist.hpp` の乱数表をコンパイル時に構築する。
`<random>` は使わない。

**理由**：乱数表は実行中に変化しない純粋なデータであり、`attack.hpp` の利きテーブルと同じ性質を持つ。
同じ形に揃えることで、「実行時に変わらないものはコンパイル時に作る」という方針がライブラリ全体で一貫する。

`std::mt19937_64` を実行時に使う場合、乱数表は名前空間スコープの非 const オブジェクトになり、
他の翻訳単位の静的初期化から参照されると初期化順序が未定義になる。
`constexpr` ならこの問題自体が存在しない。

Zobrist の乱数に要求される性質は「一様性」ではなく「互いに線形独立であること」である。
どの乱数も他の乱数の XOR の組み合わせで表現できてはならない。
splitmix64 は状態を加算で進めたうえで乗算とシフトを混ぜるため、この要件を満たす。
線形合同法の下位ビットは周期が短く XOR に対して規則的なので、採用しない。

**帰結**：乱数表がバイナリに定数として焼き込まれ、起動時のコストがゼロになる。
値が完全に再現可能なため、置換表のデバッグや、将来の完全解析データベースとの照合で
「同じ局面が同じ key になる」ことを別プロセス間でも保証できる。

### D-021　key は差分更新するが、全計算の実装を検証用に残す

**決定**：`compute_key()`（盤を全走査して key を作る）を先に実装し、
そのうえで `do_move()` / `undo_move()` に差分更新を組み込む。
`compute_key()` は削除せず、テストから使える形で残す。

**理由**：差分更新の誤りは、動作を止めずに値だけをずらす。
key が間違っていても局面は正しく進み、指し手も正しく生成される。
表に出るのは千日手の誤判定や置換表の誤ヒットという形であり、
どちらも「たまに起きる不可解な挙動」としてしか観測できない。

したがって、差分更新は自己検証できない。
独立に計算した正解と照合する以外に確かめる方法がない。
これは M2 で perft を参照実装と照合したのと同じ構図であり、
違いは「参照実装が同じヘッダの中に置ける程度に単純」という点だけである。

**帰結**：perft の全ノードで `key() == compute_key()` を検査するテストを置ける。
M2 の基準値テストが約 15 万局面を通るため、差分更新の分岐（打つ手、取る手、成る手、
にわとりを取って持ち駒がひよこになる手）はすべてこの照合を通過する。

`compute_key()` は探索の内側では呼ばない。用途は検証と、局面を新規に構築したときの初期化である。
### D-022　key の差分更新は盤を書き換える 4 つの私有関数に置く

**決定**：`put_piece()` / `remove_piece()` / `add_hand()` / `remove_hand()` の中で `key_` を更新する。
`do_move()` / `undo_move()` は手番ぶんの XOR だけを書き、駒の移動に伴う key の更新は書かない。
`undo_move()` は保存した値を書き戻さず、逆向きの XOR によって自然に元の値へ戻す。

**理由**：盤の状態は `board_`、`byType_`、`byColor_`、`hand_`、`key_` の 5 つに分散している。
これらが食い違った瞬間に局面は壊れるが、食い違いは即座には表面化しない。
`do_move()` の側に key の更新を書くと、更新すべき事実の列挙が指し手の種類ごとに分岐し、
分岐のどれか一つで書き漏らすと、そこを通る局面でだけ key がずれる。

4 つの私有関数はすでに「盤とビットボードを同時に更新する」という役割を持っており、
`key_` を加えることはその役割の自然な拡張である。
これらを通らずに盤を書き換える経路が存在しない限り、書き漏らしは構造的に起こらない。
`from_sfen()` による構築も同じ関数を通るため、構築の直後から `key_` が正しい。

`undo_move()` で保存値を書き戻さないのは、XOR が自己逆元であることを検証に使うためである。
書き戻す実装では、差分更新が非対称に壊れていても undo のたびに正しい値へ復元されてしまい、
誤りが表に出ない。逆向きの XOR に任せれば、非対称な壊れ方はそのまま key のずれとして観測できる。

**帰結**：手番の XOR だけが 4 つの関数の外に残る。
`do_move()` / `undo_move()` の手番反転と、`from_sfen()` が SFEN から手番を読む箇所の 2 か所である。
後者は `compute_key()` との照合テストで守る。

**`StateInfo::key` の意味**：その着手が上書きする直前の局面の key を保持する。
`captured`（その着手が盤から消す駒）と同じく「着手が壊す情報」であり、役割が揃う。

この向きを選ぶと、鎖は根の局面の key まで含む。
`do_move()` を一度も呼んでいない局面には `StateInfo` が存在しないため、
「着手後の key を保存する」向きにすると根の局面だけが鎖から漏れ、千日手の数え落としが生じる。

千日手判定では、現在の局面の key は `key_`、2 手前は `st_->previous->key`、
4 手前はさらに 2 つ遡った先、という形で辿る。
同一局面は必ず手番が一致するため、鎖は 2 つずつ遡ればよい。
