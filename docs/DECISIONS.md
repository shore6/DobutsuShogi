# 設計判断の記録

仕様書：[SPEC.md](SPEC.md) ／ ロードマップ：[ROADMAP.md](ROADMAP.md)

SPEC.md が「何を作るか」を定めるのに対し、本書は「なぜそう決めたか」を残す。
後から読んだときに、決定を覆してよいか（前提が変わったか）を判断できることを目的とする。

各項目には、決定・理由・帰結を記す。
帰結の欄には、その決定が壊れたときに何が起きるかを書く。

## M0：土台

### D-001　`Piece` は上位ビットに手番を置く

**決定**：1 バイトのうち bit3 を手番、bit0-2 を駒種とする。
`NO_PIECE = 0`、先手の駒が 1〜5、後手の駒が 9〜13、`PIECE_NB = 16`。

**理由**：`type_of()` がマスク 1 回、`color_of()` がシフト 1 回で済む。
手番ごとに値が連続するため、`Piece` を添字とするテーブルで「手番込みの駒」を直接引ける。
Stockfish および cshogi の慣行と一致するため、両者のコードを参照する際の読み替えが不要になる。

**帰結**：値 6, 7, 14, 15 が欠番となり、`Piece` を添字とする配列は 16 要素のうち 4 要素が無駄になる。
これは意図的な浪費である。
値を 12 個に詰めると `make_piece()` が乗算になり、さらに 16 という 2 の冪を失うことでアドレス計算からシフト最適化が消える。
M2 で作る利きテーブルは 288 バイトであり、数十バイトの無駄より計算の単純さが勝つ。

ビット配置を知るコードは `make_piece()` / `type_of()` / `color_of()` の 3 関数に限定する。
定数 `COLOR_SHIFT` と `PT_MASK` を経由させ、他の場所にビット幅の知識を漏らさない。

### D-002　筋と段の内部値は 0 起点とし、定数名で USI 表記を保つ

**決定**：`FILE_3 = 0, FILE_2 = 1, FILE_1 = 2` および `RANK_A = 0, ..., RANK_D = 3` とする。
マスの連番は `段 × 3 + 筋`。

**理由**：内部値を 0 起点に揃えれば配列添字にそのまま使える。
筋については、USI の筋番号が右から 1, 2, 3 であるのに対し内部値は左から 0, 1, 2 となり、対応が逆転する。
この逆転を `square_to_usi()` / `square_from_usi()` の 2 関数だけに閉じ込め、それ以外のコードからは 0 起点の素直な座標系だけが見えるようにする。

定数名を `FILE_3` のままにするのは、`FILE_3 = 0` という一見ねじれた対応を、名前の側で読み解けるようにするためである。

**帰結**：`'3' - 内部値` という変換が現れるのは文字列変換の内部だけである。
他のファイルにこの計算が漏れたら、座標系の設計が崩れたサインとみなす。

### D-003　番兵 `SQ_NONE` の値は 15

**決定**：`SQ_NB = 12` と別に `SQ_NONE = 15` を定義する。

**理由**：SPEC 5.3 により、`Move` はマスを 4 ビットのフィールドに格納する。
番兵が 4 ビットで表せる値であれば、`Move` の中に `SQ_NONE` をそのまま置ける。

**帰結**：この値はバイナリ表現の一部であり、後から変更すると `Move` の互換性が失われる。
M0 の時点で確定させたのはこのためである。

### D-004　変換関数は例外を投げず、番兵を返す

**決定**：`square_from_usi()` は不正な入力に対して `SQ_NONE` を返す。
`square_to_usi()` は盤外のマスに対して空文字列を返す。
SPEC 6.4 の指し手解釈と同じ方針である。

**理由**：これらの関数は SFEN や USI コマンドの解釈で使われる。
外部入力の不正は例外的事態ではなく想定内の事象であり、呼び出し側は必ず失敗を扱う必要がある。
例外にすると、探索から呼ばれる経路で例外処理のコストを負う可能性も残る。

**帰結**：呼び出し側は戻り値の検査を怠ってはならない。
検査漏れは `SQ_NONE` が盤の座標として流れ込む形で顕在化する。

### D-005　列挙型は `enum class` ではなく素の `enum` を使う

**決定**：`Color`, `PieceType`, `Piece`, `File`, `Rank`, `Square` はすべて素の `enum` とし、基底型に `std::uint8_t` を明示する。

**理由**：`enum class` は暗黙の整数変換を禁じるため型安全だが、`attacks[pt][c][sq]` のような添字アクセスのたびに `static_cast` が必要になる。
コアの中心となる指し手生成が添字操作の塊であることを考えると、可読性の損失が型安全性の利得を上回る。

基底型の明示は性能目標に直結する。
省略すると処理系は `int` を選び、`Piece board_[12]` が 12 バイトから 48 バイトへ膨らむ。
SPEC 10 節の「局面のメモリ 64 バイト以内」はこの指定に依存している。

**帰結**：型の取り違え（`PieceType` を `Piece` として渡すなど）をコンパイラが検出しない。
引数名の規約（`PieceType` は `pt`、`Piece` は `pc`、`Square` は `s`）でこれを補う。

なお素の `enum` であっても、演算結果は整数昇格により `int` になる。
enum 型を返す関数では明示的なキャストが必要である。

### D-006　ビルド構成は 3 ターゲット

**決定**：`dobutsu_core`（静的ライブラリ）、`dobutsu_cli`（実行ファイル）、`dobutsu_tests`（テスト）に分ける。
ヘッダ検索パスと C++20 要求は `dobutsu_core` に `PUBLIC` で付け、利用側へ伝播させる。

**理由**：コアを CLI から独立させることで、SPEC 8 節の USI 層や将来の Python バインディングを、CLI を巻き込まずに追加できる。
「コアは標準ライブラリ以外に依存しない」という制約が、ターゲットの依存グラフとして表現される。

**帰結**：GoogleTest への依存は `dobutsu_tests` だけが持つ。
`DOBUTSU_BUILD_TESTS=OFF` にすれば、ネットワーク接続なしでコアと CLI をビルドできる。

## M1：盤面表現と SFEN

### D-007　`Bitboard` は `uint16_t` の型別名ではなくクラスにする

**決定**：`using Bitboard = std::uint16_t;` ではなく、`std::uint16_t` を 1 個だけ持つクラスとして定義する。
集合演算は演算子オーバーロードで提供する。

**理由**：型別名にすると、`Bitboard` と「駒の枚数」と「マスの連番」がすべて同じ型になる。
ビットボードは添字ではなく値として関数間を渡り歩くため、引数の取り違えをコンパイラに検出させる価値が高い。

D-005 で `enum class` を退けた判断と方向が逆に見えるが、対象の性質が異なる。
`Square` や `PieceType` は配列の添字として使うことが主目的であり、暗黙変換の禁止が直接コストになる。
`Bitboard` は添字にならないため、そのコストが発生しない。

**帰結**：クラスにしたことで、`sizeof(Bitboard) == 2` が設計上の要件になる。
メンバに非 static な定数を持たせるとサイズが倍になり、SPEC 10 節の局面サイズ制約に波及する。
盤マスクの類は必ず `static constexpr` とすること。

### D-008　上位 4 ビットは常に 0 とし、不変条件を破れる箇所でのみマスクする

**決定**：`uint16_t` 16 ビットのうち bit12-15 は常に 0 に保つ。
盤マスク `0x0FFF` を掛けるのは `explicit Bitboard(std::uint16_t)` の 1 箇所のみとし、
補集合 `operator~` はその コンストラクタを経由して結果を構築する。

**理由**：`popcount()` は集合の要素数を返す契約であり、盤外のビットが混ざると値が狂う。
一方で `&` や `|` は両辺が不変条件を満たしていれば結果も満たすため、マスクは不要である。
全メソッドで防御的にマスクすると、指し手生成のホットパスに無駄な AND が並ぶ。

**帰結**：不変条件を知るコードは コンストラクタ 1 箇所に閉じる。
新たに `uint16_t` から `Bitboard` を作る経路を増やす場合は、必ずこのコンストラクタを通すこと。

### D-009　`lsb()` と `set()` / `reset()` は引数の妥当性を検査しない

**決定**：`lsb()` および `pop_lsb()` は集合が空でないことを、
`set()` / `reset()` / `test()` は `is_ok(s)` が真であることを、呼び出し側の責任とする。

**理由**：これらは M2 の指し手生成の最内周から呼ばれる。
D-004 で文字列変換に番兵方式を採ったのと異なり、ここでは不正な入力は外部からではなく実装の誤りとしてのみ発生する。
実行時に検査しても、返せる意味のある値が無い。

**帰結**：`square_from_usi()` が返した `SQ_NONE` を検査せずに `set()` へ渡すと、
bit15 が立って `popcount()` が実在しないマスを数える。
症状はビットボードの要素数の狂いとして、原因から離れた場所に現れる。
外部入力に由来する `Square` は、ビットボードに触れる前に検査すること。

### D-010　持ち駒は 1 駒種 2 ビット、片側 6 ビットに詰める

**決定**：`std::uint16_t hand_[COLOR_NB]` の下位 6 ビットを使う。
bit0-1 にきりん、bit2-3 にぞう、bit4-5 にひよこの枚数を置く。
上位 10 ビットは常に 0 とする。

駒種からシフト量への対応は `constexpr` の表で与え、`(pt - GIRAFFE) * 2` のような算術で導かない。

**理由**：持ち駒になりうるのはきりん・ぞう・ひよこの 3 種だけである。
ライオンは取られた時点で対局が終わるため持ち駒にならず、にわとりは取られるとひよこに戻る。
各駒種は盤上に 2 枚しか存在しないため、枚数の上限は 2 であり 2 ビットで表せる。

この配置は SPEC 5.6 のパック表現（持ち駒 12 ビット）とビット幅が一致する。
`hand_[BLACK] | (hand_[WHITE] << 6)` の連結だけでパックでき、詰め直しの変換関数が不要になる。

「持ち駒が 1 枚もない」の判定が `hand_[c] == 0` の 1 比較で済む点も、配列表現に対する利点である。
SFEN 生成と M3 のハッシュ更新で頻出する。

**帰結**：枚数の上限 2 に対して 2 ビットは 0〜3 を表せるため、余裕は 1 段しかない。
規則違反の局面（同じ駒種が 3 枚以上）を作ると隣の駒種のフィールドを侵食する。
SFEN 解析は枚数の妥当性を検査してから格納すること。

シフト量を算術で導かないのは D-001 と同じ理由による。
`GIRAFFE = 2` という `PieceType` の値と、持ち駒フィールドの並び順は、たまたま一致しているだけの別概念である。

### D-011　盤配列とビットボードの更新は 2 つの private 関数に集約する

**決定**：`board_` / `byColor_` / `byType_` を書き換える操作は `put_piece()` と `remove_piece()` の 2 つだけとし、
どちらも 3 者を同時に更新する。他のメンバ関数はこの 2 つを経由する。

**理由**：SPEC 5.4 は同じ情報を配列とビットボードの両方に持つことを定めている。
冗長性そのものは意図した取引だが、更新箇所が散らばると 3 者の同期が崩れる。
D-008 で不変条件を守る箇所をコンストラクタ 1 つに閉じたのと同じ構造を、ここでも作る。

**帰結**：同期の崩れは、盤面表示は正常なのに指し手生成だけが誤る、という形で現れる。
症状が原因から遠いため、整合性を検査する関数を用意し、テストから呼ぶ。
検査は「`board_` を走査して構築したビットボードが `byColor_` / `byType_` と一致するか」で足りる。

### D-012　`from_sfen()` は `std::optional<Position>` を返す

**決定**：SFEN の解析に失敗した場合、`std::nullopt` を返す。例外は投げない。

**理由**：D-004 および SPEC 6.4 と同じ方針である。
外部入力の不正は想定内の事象であり、呼び出し側は必ず失敗を扱う必要がある。

`Square` と異なり `Position` には番兵として使える値がない。
「空の局面」を失敗値に流用すると、正当な空盤面と区別できなくなる。
`std::optional` は失敗の可能性を戻り値の型として表現するため、検査漏れがコンパイル時に検出される。

**帰結**：SPEC 6.1 の宣言を `static std::optional<Position> from_sfen(std::string_view)` に改める。
コアライブラリの標準ライブラリ以外への非依存は保たれる。

### D-013　`to_ascii()` は SFEN と別の表記を持ち、解析の対象としない

**決定**：ASCII 表示ではにわとりを `H` の 1 文字で表し、持ち駒・手番・手数にラベルを付ける（SPEC 3.5）。
この書式を読み戻す関数は用意しない。

**理由**：盤面のマスは 1 文字幅なので、SFEN の `+C` をそのまま置くと桁が揃わない。
表示は人が読むためのもので、揃った格子であることが可読性の大半を占める。

持ち駒に `hand:` のラベルを付けるのは、持ち駒がないときの空行と、
表示の不具合で消えた場合とを区別できるようにするためである。
手番と手数を含めるのは、この文字列がデバッグ時に「局面の全情報」として読まれるためで、
手番の取り違えは指し手生成の誤りという遠い症状として現れる。

**帰結**：文字列から局面を復元する経路は SFEN 1 本に保たれる。
往復テスト（SPEC 9.3）の対象は `sfen()` と `from_sfen()` だけであり、
`to_ascii()` は出力を固定文字列と比較する形で検証する。

表示書式を変えるとそのテストが落ちる。これは意図した挙動で、
表示は仕様であり実装の都合で動かしてよいものではない、という位置づけを保つ。

## 決定を覆すときの手順

前提が変わって決定を見直す場合は、該当項目を削除せず、決定と理由を書き換えたうえで変更の経緯を追記する。
バイナリ表現に関わる決定（D-001, D-003）の変更は、置換表と将来の完全解析データベースの互換性に波及する。
