# 開発ワークフロー

仕様書：[SPEC.md](SPEC.md) ／ ロードマップ：[ROADMAP.md](ROADMAP.md) ／ 設計判断：[DECISIONS.md](DECISIONS.md)

本書は、このプロジェクトを「ユーザーの学習を通じて進める」という方針を、
実際の手順と注意点として書き下したものである。

方針そのものは [CLAUDE.md](../CLAUDE.md) に置く。
本書はその運用、すなわち「毎回どういう順番で何をするか」「どこで失敗しやすいか」を扱う。

---

## 1. 役割分担

| | 担当 |
| --- | --- |
| コードを書く | ユーザー |
| 設計・API の決定・選択肢の提示 | アシスタント |
| レビュー | アシスタント |
| ドキュメントの更新 | アシスタント |
| テストの観点の提示 | アシスタント |
| テストコードを書く | ユーザー |

**アシスタントは完成したコードを書いて渡さない。**
これは効率のための制約ではなく、目的そのものである。
ユーザーが書いて詰まり、指摘を受けて直す過程が、このプロジェクトの成果物の半分を占める。

ただし、レビューの中で**数行の断片**を示すのは構わない。
「`>=` に直す」「`continue` を足す」のように、直す内容が一意に定まる箇所は
文章で説明するより短いコードで示した方が速く、学習の妨げにもならない。
関数まるごと、あるいはファイルまるごとを書くのは方針違反である。

境目の目安は「その断片を写しても、その関数の設計判断は残っている」かどうかである。

## 2. 1 ファイルあたりのサイクル

```
設計ブリーフ  →  ユーザーが実装  →  レビュー  →  修正  →  （必要なら再レビュー）  →  次のファイル
                                      ↓
                              設計判断が出たら DECISIONS.md
```

### 2.1 設計ブリーフ

ファイル（または小さなまとまり）に着手する前に、次を示す。

- **そのファイルが何を担うか**、依存関係のどこに位置するか
- **公開する API の一覧**（シグネチャまで。中身は書かない）
- **決めておくべき表現**（ビット配置、テーブルの形、エラーの返し方）
- **つまずきやすい点**を先回りで 2〜4 個
- **テストで確認すべき観点**

分量は多くてよい。実装の指示ではなく、実装のための地図である。

C++ の記法や標準ライブラリの知識に穴があることを前提にする。
`std::from_chars` の戻り値の形、`std::string_view` と `std::string` の違い、
`constexpr` を書ける場所、といった説明は毎回入れてよい。
CMake については前提知識ゼロとして扱い、必要な操作をそのまま示す。

### 2.2 選択肢の提示

設計上の分岐は、**選択肢を並べて推奨を明示する**形で出す。

- 案は 2〜3 個。それ以上は判断を助けない
- 各案について「何ができなくなるか」を書く。利点だけの比較は選べない
- 推奨を 1 つ決めて、その理由を書く
- 決まったら **その場で** DECISIONS.md に記録する

「どちらでもよい」で終わらせない。
どちらでもよい選択なら、アシスタントが決めて通知するだけでよい。

### 2.3 ドキュメントの更新

**ユーザーに投げない。** 設計判断が出た瞬間に更新する。

| 出来事 | 更新先 |
| --- | --- |
| 表現・書式・API を決めた | SPEC.md |
| 「なぜそう決めたか」が残る決定をした | DECISIONS.md |
| マイルストーンが完了した | ROADMAP.md |
| ビルド手順が変わった | BUILD.md |

決定を**変更**したときは、変更後の内容だけを書かず、
「当初はこうだったが、こういう理由で変えた」を残す。
D-014 がその形になっている。

## 3. レビューの方法

このプロジェクトで最も効果が出ている部分であり、最も手間がかかる部分でもある。

### 3.1 主張せず、実演する

「ここはバグっている」と書くだけでは伝わらない。
スクラッチパッドに切り出してコンパイルし、実際に走らせて出力を見せる。

```
[gle/1c1/1C1/ELG b - 1] -> nullopt
```

この 1 行があると、「`/` の分岐に `continue` がないので正しい SFEN が全部弾かれる」という説明が
一読で腑に落ちる。実演のない指摘は、正しくても納得されにくく、直し忘れが起きる。

未定義動作のように出力に出ないものは、観測できる形に加工する。
`Position` のコピーにアクセサを足してビットボードの生の値を表示させ、
`byType_[GIRAFFE]` が `0x801` から `0x1801` に変わる（ビット 12 が立つ）ところを見せた例がある。

### 3.2 コンパイルエラーは「原因の数」で数える

12 個のエラーが出ていても、原因が 4 種類なら 4 項目として提示する。
実際に `Position::` の書き忘れ 1 件が 9 個のエラーを生んだことがある。

エラーメッセージを上から順に列挙するのは、レビューとしては何もしていないに等しい。
**どれが原因で、どれが波及か**を分けるのがレビューの仕事である。

### 3.3 コンパイルエラーの裏に論理バグが隠れている

ビルドが通らない状態のコードには、コンパイルエラーに隠れて論理バグが同居していることが多い。

有効な手順は次のとおり。

1. ユーザーのファイルをスクラッチパッドにコピーする
2. **機械的な修正だけ**を当てる（綴り、型、アクセス修飾子）
3. 動く状態にして、実際の入力を通す
4. 出てきた論理バグを、コンパイルエラーとは別立てで報告する

この手順で、SFEN パーサから 5 件の論理バグ（`continue` 抜け、`-` の拒否、
`+C` がひよことして置かれる、`sfen()` がにわとりを `H` と書く、段数を検査していない）を
一度に洗い出した例がある。

### 3.4 提示の順序

重い順に並べる。優先度は「正しさ」→「安全性」→「設計」→「書き方」。

1. 未定義動作・データの破壊
2. 誤った結果を返す
3. 検査の抜け
4. 重複・責務の混在
5. 綴り、未使用の `#include`、命名

各項目は「何が起きるか」「なぜそうなるか」「どう直すか」の 3 点を揃える。
「どう直すか」だけを並べたリストは、写して終わりになる。

### 3.5 良かった点を先に短く書く

3.4 の順序で並べると指摘だけが並ぶので、冒頭に確認できた事実を置く。
「`sfen()` は一発で正しい」「`split()` は直っている」のように、
**検証した結果として**書く。褒め言葉ではなく、レビュー範囲の報告として扱う。

## 4. テストの扱い

### 4.1 「テストが緑」は「検証できている」ではない

このプロジェクトで実際に起きたこと。

- アサーションが 1 つもない空のテストが、`22/22 パス` の中に紛れていた
- `put_piece()` からビットボードの更新を丸ごと削っても、既存のテストは全部通った
- `to_ascii()` の分岐のうち、持ち駒あり・後手番の経路が一度も実行されていなかった

**カバレッジではなく、テストを壊す側から測る。**

### 4.2 突然変異テスト

実装をわざと壊してテストが落ちるかを確認する。
落ちなければ、そのテストはその箇所を検証していない。

```
sed で 1 か所書き換える → テスト実行ファイルを作る → 落ちるか見る
```

M1 では 19 通りの変異を当て、生存が 11 件から 2 件に減るまでテストを足した。
どの検査が実際に効いているかが分かるので、テストの追加が当てずっぽうでなくなる。

### 4.3 殺せない変異を区別する

生存＝テスト不足、ではない。**原理的に観測できない変異**が混ざる。

- 範囲外書き込みの境界（`>` と `>=`）— どちらも同じ値を返し、違いは配列外に書くかどうかだけ
- 将来のための防御的検査 — 今その状態を作る経路が存在しない

これらは「テストが足りない」ではなく「今の設計では観測できない」として、
理由とともに SPEC.md 9.4 に記録する。
区別せずにカバレッジを追うと、意味のないテストを書くことになる。

### 4.4 検証の錨を 1 本置く

往復テスト（`sfen()` → `from_sfen()` → `sfen()`）は、
両者が**同じだけずれていれば**通ってしまう。

`Position::startpos().sfen()` を固定文字列と比べるテストが 1 本あると、
この対称性が破れる。実際、`from_sfen` で `ply+1`、`sfen` で `ply-1` とする変異は
このテストだけが検出した。

**往復テストには必ず、片側だけを固定値で押さえるテストを添える。**

### 4.5 異常系は拒否理由ごとに 1 つ

1 つの入力が複数の理由で拒否されると、そのうち 1 つの検査を消してもテストが落ちない。
「手数 0」を試すつもりの入力が、手番の綴り間違いで先に弾かれていた例がある。

拒否理由の一覧を作り、各理由について**他の理由では拒否されない入力**を用意する。
SPEC.md 9.3.1 がその一覧である。

### 4.6 実装の順序でテストを助ける

出力側（`sfen()`）を先に書かせると、それ自体を固定文字列で検証でき、
入力側（`from_sfen()`）を直すときの基準として使える。

逆順にすると、両方が未検証のまま往復テストだけが通る状態になりやすい。
**依存の少ない側から書かせる**のはテスト戦略の一部である。

## 5. 繰り返し出てくる注意点

### 5.1 契約を書いたら、呼ぶ側で守る

`put_piece()` や `add_hand()` のように「範囲の保証は呼び出し側の責任」と決めた関数は、
契約が破られた時点で以降の状態が保証されなくなる。

`from_sfen()` が枚数を確認せずに `add_hand()` を呼び、
2 ビットのフィールドが隣の駒種に繰り上がって、
**下流の整合性検査をすり抜けた**ことがある。

「下流で弾かれるはず」は根拠にならない。契約は呼ぶ側で守る。

### 5.2 警告を無視しない

`-Wall -Wextra` は有効になっている。
実際に検出された例。

- `-Wenum-compare` — `Piece` と `PieceType` の比較。先手の駒だけ偶然通り、後手が黙って弾かれていた
- `-Wunused-but-set-variable` — 中身が空のテスト
- `-Wrange-loop-construct` — 範囲 for での意図しないコピー
- `-Wsign-compare` — `int` と `size_type`

ビルド出力に警告が残っている状態で「動いた」としない。

### 5.3 型の取り違えをコンパイルエラーにする

`Piece` と `PieceType` の比較が警告で済んだ事故を踏まえ、
新しく増える型は `enum class` にして、混同をコンパイルエラーにする（D-014）。

既存の `Square` や `File` は配列の添字として整数の性質を使うため、
そのまま非スコープの `enum` で残す。**一律にしない。**

### 5.4 無効値の居場所

失敗を表す方法を、型に応じて使い分ける。

| 型 | 無効値 | 理由 |
| --- | --- | --- |
| `Square` | `SQ_NONE` | 12〜15 が空いている |
| `Move` | `Move::NONE`（= 0） | `from == to` はあり得ない |
| `Position` | `std::optional` | 空き値がない |

**型の中に無効値の居場所があるか**で決める。

### 5.5 出力の宛先

CLI の標準出力には「その道具が生産した結果」だけを流す。
バージョン表示やデバッグ用のダンプが混ざると、パイプやリダイレクトで使えなくなる。

M1 の CLI に M0 のデバッグ出力が残っており、
**解析に失敗して終了コード 1 を返しているのに標準出力に 6 行出ている**状態になっていた。

判断の基準は「この出力をファイルに保存したいか」。

## 6. この方式のコスト

レビューに実演を伴うため、1 ファイルあたり数往復かかる。
M1 の `src/position.cpp` は 3 回のレビューを要した。

その代わり、M1 の完了時点で次が得られている。

- ソースの論理バグ 11 件（うち未定義動作 1 件）を、テストが書かれる前に除去
- テストの穴 11 件を突然変異テストで特定し、2 件（いずれも観測不能）まで削減
- 設計判断 15 件が理由とともに記録され、後から覆せる状態

速度を上げたい場合に削ってよいのは 3.1（実演）ではなく、
設計ブリーフの網羅性である。実演を省くと、指摘が伝わらず同じバグが再発する。

## 7. 出力スタイルとの関係

このセッションは「Learning」出力スタイルで動作しており、
`★ Insight` ブロックによる補足と、`TODO(human)` を置いて実装を依頼する
「Learn by Doing」の仕組みを持つ。

本プロジェクトでは **`TODO(human)` 方式は使わない。**
全コードをユーザーが書くため、依頼すべき箇所を特定する必要がないからである。
設計ブリーフ（2.1）がその役割を果たす。

`★ Insight` は継続して使う。
ただし一般的なプログラミングの解説ではなく、
**このコードベースに固有の事実**を書く。
「なぜ `SQ_NONE` が 12 ではなく 15 なのか」は書く価値があるが、
「ビット演算とは」は書かない。
